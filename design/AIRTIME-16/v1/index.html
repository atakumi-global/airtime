Airtime design system and product screens

A coded design direction for Airtime in Plane's visual language: a token foundation, core components, the Windows shell, every v1 screen, the future consent and AI screens, and a clickable prototype built from the same parts. Static HTML here for review; the deliverable itself is a React and TypeScript package.

Plane tokens reused Light and dark WCAG 2.2 AA target Covers AIRTIME-17 to 24
Start with the foundation Open the prototype

Rationale

Three directions were weighed: (1) a strict Plane-native extension, (2) a time-first workspace led by an amber running accent, and (3) separate member and manager surfaces. The chosen path is Plane-native with one deliberate addition: the always-visible timer is promoted to a first-class, persistent surface, and role separation is expressed inside one visual language rather than two. That keeps Airtime recognisably part of the Plane ecosystem while making its own core object — the running timer and the budget it feeds — impossible to miss.

How to review

  • Use Light and Dark in the top bar on any page.
  • Each screen page groups states side by side; blocked and disabled states are shown, not hidden.
  • The prototype is interactive; try start/stop, back-fill, budget and export.
  • Resize to 375px to check the compact layout; the desktop shell targets Windows at 1024px and up.

Version log

v1 — initial design
25 Sep 2026 · First complete pass: foundation, components, shell, all screens, prototype.

Known limitations

  • These are static HTML design references. The shipped deliverable is the React and TypeScript package; minor spacing is expected to move by a pixel or two in build.
  • Charts are drawn as SVG by hand, not a charting library. The library choice and its AGPL-3.0 compatibility are still open on AIRTIME-16.
  • The icon set reuses Plane's visual language; the final AGPL-compatible set is still to be confirmed.
  • Tray, notification and window-chrome behaviour must be validated against the Tauri v2 Windows capability matrix before build.
  • Right-to-left and localisation were not in scope for v1 and would need a layout pass.

Decisions to confirm

  • Is promoting the timer bar to a persistent surface the right emphasis, or should it stay a screen-level control?
  • Should budget health use the existing success/warning/danger tokens, or its own distinct pair?
  • Is a fully accessible tray and notification set in scope for v1, or deferred with the rest of the shell polish?
